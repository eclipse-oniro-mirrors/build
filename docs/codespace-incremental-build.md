# 在 CodeSpace 中使用预热产物增量编译

本指南面向已预置 OpenHarmony 源码和配套构建产物的 CodeSpace 环境。下面分别列出 `x86_64_virt` 和 `wukong100` 的命令；请选择与预热产物一致的产品及构建参数，保留项目原有的额外构建参数。

## 1. 为什么可以直接增量编译

全新代码从零构建通常需要较长时间。每日远程流水线提前完成产品构建，CodeSpace 获取代码时一并获取配套产物，开发者可以在已有构建状态上继续修改、编译和验证。

交付内容需要配套，包括源码、工具链、生成文件、`out/` 中的构建图和中间产物，以及成功构建基线。只有最终镜像，不能替代增量构建所需的中间状态。

```mermaid
flowchart LR
    A[每日远程流水线构建] --> B[源码与配套产物一起交付]
    B --> C[CodeSpace 获取工作区]
    C --> D[修改代码并增量编译]
    D --> E[成功后更新构建基线]
```

本文适用于已启用 `build_framework_enable_incremental_build`、并由环境提供方准备好增量工作区的产品。开发者继续使用 `build.sh`，通常不需要手动创建路径映射或执行基线脚本。

## 2. 开始前确认什么

1. 进入 OpenHarmony **源码根目录**，即能看到 `.gn`、`build.sh`、`build/`、`foundation/`、`out/` 的目录。不要在 `build/` 仓目录中执行产品构建。
2. 保留工作区自带的源码、工具链、生成文件和 `out/`。不要为了开始增量编译先执行清理，或仅将另一份工作区的 `out/` 拼接进来。
3. 使用与预热版本一致的产品、构建类型及其他构建参数。切换产品或工具链时，需要对应的构建状态。
4. 保存本地修改。首次进入迁移后的工作区，也可以先修改代码再构建；入口会校验输入，真实修改仍需按依赖重编。

下面三种编译方式均从源码根目录执行，每种方式按产品选择对应命令。

## 3. 三种常用编译方式

### 3.1 完整产品构建入口

`x86_64_virt`：

```bash
./build.sh --product-name x86_64_virt --ccache
```

`wukong100`：

```bash
./build.sh --product-name wukong100 --ccache
```

这是日常完整产品构建命令。已有配套产物时，构建系统会按依赖增量执行，并非每次都从零编译所有文件。

不确定是否可以跳过配置生成，或者修改了 GN、产品配置、部件清单、构建参数时，优先使用这条命令，让构建准备及配置生成按正常流程执行。

### 3.2 未修改 GN 时，可选择快速增量

`x86_64_virt`：

```bash
./build.sh --product-name x86_64_virt --ccache --fast-rebuild
```

`wukong100`：

```bash
./build.sh --product-name wukong100 --ccache --fast-rebuild
```

适用于已有成功构建状态，且仅修改 CPP 等源码、构建配置保持不变的情况。`--fast-rebuild` 会跳过部分构建准备和 GN 生成阶段，继续复用已有构建图。

以下情况应去掉 `--fast-rebuild`，使用上一条完整产品命令：

- 修改 `BUILD.gn`、`*.gni`。
- 新增或移除源码文件，并调整目标的源文件列表或依赖。
- 修改产品配置、`bundle.json` 等会影响构建图的配置。
- 切换产品、构建目录，或修改 GN 参数、工具链等编译配置。
- 入口提示需要重新生成 GN，或者当前工作区缺少对应构建图。

`--fast-rebuild` 不会跳过必要的源码依赖判断。真实修改仍可能触发编译、链接、资源处理和打包。

### 3.3 单独编译某个模块

`x86_64_virt`：

```bash
./build.sh --product-name x86_64_virt --ccache --build-target <模块目标>
```

`wukong100`：

```bash
./build.sh --product-name wukong100 --ccache --build-target <模块目标>
```

将 `<模块目标>` 替换为实际构建目标，执行时不要保留尖括号。目标应来自对应的 `BUILD.gn`，不能直接把子系统名当作目标。

如果短名称存在重名或提示 `unknown target`，使用 `目标所在目录:目标名` 的完整形式，例如 `commonlibrary/c_utils/base:utils`。部件目标也可以使用 `out/<device>/build_configs/<subsystem>/<part>:<part>` 形式，具体以当前产品生成的目标为准。

单目标构建只构建该目标及其依赖。需要安装后的完整产品镜像时，再使用 3.1 或 3.2 的产品命令，完成对应的安装和打包流程。

## 4. 修改不同内容时怎么选择

| 修改内容 | 建议方式 | 需要关注 |
| --- | --- | --- |
| 已有 CPP 中的函数实现 | 完整产品命令，或符合条件时使用 `--fast-rebuild` | 对应目标可能重新编译，相关库可能重新链接。 |
| 已有头文件 | 构建配置未变时，可使用 `--fast-rebuild` | 被多个目标引用时，触发较多重编属于正常依赖传播。 |
| GN、源文件列表、目标依赖或产品配置 | 完整产品命令，不加 `--fast-rebuild` | 先更新构建图，再由新图决定执行范围。 |
| IDL、JSON、脚本、资源等非 CPP 文件 | 按是否影响构建图选择命令；不确定时用完整产品命令 | 已声明为构建依赖的输入同样参与增量判断；生成和打包动作可能重跑。 |
| 只验证某个模块能否编译 | 使用 `--build-target` | 模块编译成功不代表已经完成镜像打包或运行验证。 |

## 5. 为什么迁移目录后仍能使用已有产物

远程流水线和 CodeSpace 的源码目录可能不同，而 CMake 缓存、构建命令或依赖信息仍引用原绝对路径。增量入口在需要时通过 bwrap 建立私有挂载视图，让构建进程通过原逻辑路径访问当前工作区。

映射只对本次构建进程及子进程生效，新增产物仍写入 CodeSpace 中的真实工作区。开发者无需在宿主机手动建立全局软链接，也无需逐项改写构建缓存中的路径。

路径映射后还会校验输入。已验证内容未变的输入可以恢复基线时间，迁移后的真实修改则保留并进入正常依赖判断。不要通过批量 `touch` 或手动改时间来强行消除构建动作。

如果提示缺少 bwrap、挂载命名空间不可用或工具链不匹配，请保留报错并联系环境提供方处理。不要绕过校验继续使用不匹配的产物。

## 6. 怎么判断本次构建已经结束

关注两部分输出：

1. **编译结果**：确认产品或指定目标构建成功，且没有最终失败信息。
2. **成功基线收尾**：启用增量功能的构建会在成功后保存本次状态，日志以 `incremental workspace:` 开头。等待收尾完成、命令返回，并确认退出状态成功。

产品成功日志中的 `Cost Time` 与整个命令的实际耗时可能不同：该日志之后仍可能有基线收尾。统计开发等待时间时，应以命令开始到最终返回为准。

模块构建会保留本次请求的目标范围，不会将其他尚未构建的修改确认成已成功。

## 7. 常见问题

### 没改代码，为什么还有构建动作或等待时间

增量构建仍需加载和检查构建图、依赖及输出状态。生成文件、目录时间、缺失输出或既有构建规则也可能触发 action、stamp 或打包动作。首次迁移后的校验开销可能高于后续同目录构建，不能仅按终端显示的目标数量判断总耗时。

### 修改一个 CPP，为什么还要链接或打包

源文件对应的对象文件改变后，依赖它的库需要链接；需要产品镜像时，还可能继续安装模块和打包。这些属于修改传播后的正常构建步骤。

### 修改 GN 后误用了 fast-rebuild，怎么办

去掉 `--fast-rebuild`，保留原来的产品和其他构建参数，重新执行完整产品构建命令，让配置和构建图更新。

### 新增文件后没有触发编译，先查哪里

确认文件已保存，已纳入目标的源文件列表或对应生成规则，目标已纳入当前产品，并检查是否误用了 `--fast-rebuild`。仅在磁盘上新增 CPP，不代表它已经进入构建图。

### 目录迁移后出现 CMake 路径不一致报错，怎么办

使用工作区的 `build.sh` 入口，并确认交付的是配套源码、产物和增量基线。保留首条实际错误、构建命令和完整日志，交给环境提供方核对路径映射及交付版本；不要直接覆盖 CMake 缓存或删除整份 `out/` 来掩盖问题。

### 可以同时在同一份 out 下运行两次构建吗

不要并发构建同一物理输出目录。需要同时验证不同修改时，使用各自独立的工作区和输出状态。
